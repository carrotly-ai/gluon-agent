## Changed

Version 0.13.0 introduces objective-driven campaigns: dependency-ordered tasks,
parallel isolated worktrees, task/objective verification, local integration,
autonomy checkpoints, and an operator task graph. It incorporates the security,
concurrency, Redis recovery, and UI fixes shipped since 0.12.1. See
[CHANGELOG.md](../../CHANGELOG.md) for the complete release notes.

Release-preparation changes add bounded database readiness, explicit refusal of
unsupported merge-queue retries, application dependency audit gates, and grouped
maintenance. Undeliverable chat questions remain available to eligible transports.
Installed package metadata is now the source of the CLI version, and published
images receive the package version, source commit, and UTC build timestamp.
Docker publishing first scans a local amd64 image and blocks on high or critical
OS/library findings, including unfixed vulnerabilities. The complete report
retains all severities as a workflow artifact. This gate does not replace ARM64
or live production qualification.

The container uses a digest-pinned Python 3.12/Trixie base, uv 0.13.3, and a locked
Vercel 64.7.0 installation. The existing scoped compatibility overrides are
retained; unsupported dependency substitutions were not introduced.

### Upgrade and rollback

1. Record the current image digest and application version. Back up the SQLite
   database while writers are stopped, or use SQLite's online backup mechanism.
   Copying an active database without its WAL is not a valid backup.
2. Configure authentication before exposing a non-loopback listener. Use the
   documented allowed-origin list for a separately hosted UI. Review
   [AUTH.md](../AUTH.md); do not disable authentication to bypass an upgrade issue.
3. Choose an explicit loop autonomy level. Direct loop creation defaults to L3;
   L1/L2 pause after the surveyor creates a plan. Completed worktree tasks
   integrate into the local source branch, independently of GitHub PR merging.
4. Validate both `/api/health` and `/api/ready` on the candidate. Keep automatic
   container restarts tied to liveness; readiness failures should stop traffic
   and trigger investigation, not cause restart loops under transient DB locks.
5. Verify authentication, a read/write operation, a representative campaign, and
   any enabled chat transports before accepting production traffic.
6. If rollback is needed, stop candidate writers and restore the previously
   recorded image plus its consistent database backup. Do not assume old code
   safely understands newly persisted campaign state.

The API and CLI retain their merge-queue retry entry points, but now reject the
operation explicitly because no background processor exists. Use the run's Merge
action or its GitHub PR. Historical entries and cancellation remain available.
Earlier unused advanced Git mutation and formula detail/validation HTTP routes
were retired; [API.md](../API.md) lists the supported surface.

## Found

### GitHub controls

`main` now requires a pull request, an up-to-date `pr-check` from GitHub Actions,
CodeQL from GitHub Advanced Security, and resolved conversations, including for
administrators. Force pushes and branch deletion are prohibited. Mandatory review
count is zero so the solo maintainer can merge their own reviewed PR; automatic
merging remains disabled.

CodeQL default setup covers Python, JavaScript/TypeScript, and Actions with weekly
scanning. Dependabot security updates are enabled. Grouped maintenance configuration
becomes active when merged. Both web locks remain intentionally supported; when a
bot updates the shared manifest, reconcile and validate both frozen graphs before
merging. `pr-check` also requires application dependency audits.

The default branch still has 103 Dependabot alerts (3 critical, 48 high, 39
moderate, 13 low) pending integration and GitHub re-evaluation. The candidate's
clean application audits do not close default-branch alerts before merge.
Fresh CodeQL and secret-scanning open-alert counts are zero.
